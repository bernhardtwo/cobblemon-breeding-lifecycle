# 0009 · Reference daycare keeps offspring in its own store

Status: accepted (2026-10-21)

## Context
S8 asks that a breeding in the reference daycare touch a single persistent store. S12 says the offspring is
generated by `/daycare breed`, but not where it goes. Putting it straight into the party or PC would make one
breeding edit two stores that are saved at different moments ([0006](0006-breeding-atomicity.md)).

## Decision
- `DaycareData`, one `SavedData` in the overworld, holds each player's deposited parents and pending offspring.
- `breed` adds the offspring there; `withdraw` later moves parents and offspring to the party (overflowing to the PC).
- Two places per player; a third `deposit` is refused, and `breed` needs both places filled.
- `/daycare` is always registered and reads `referenceDaycare.enabled` on every call, so a reload switches it.
- The audit's player is passed to `LifecycleService.evaluate(..., owner)`, since a Pokémon outside any store has no owner.
- A stored Pokémon that fails to load is logged and skipped instead of failing the world load.

## Consequences
- A crash during a breeding leaves it entirely done or not done; there is never an offspring without the roll.
- Offspring wait in the daycare until withdrawn; there is no limit on how many accumulate.
- `deposit` and `withdraw` are transfers between two stores and keep the window described in 0006.
